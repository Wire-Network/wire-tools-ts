# Nonbootstrap roster replacement

A real replacement posts depot collateral, starts its daemon and joins the scheduled roster. The scenario reads both deployed outposts, then executes the fresh Ethereum custody/shadow/redemption journey. It requires the replacement's accepted Ethereum delivery digest and its recorded Solana consensus vote matching the accepted envelope audit checksum, with the destination cursor already past that epoch. Chunk staging and stale transaction success are insufficient. No bootstrap-only account is accepted as replacement evidence. Run with the canonical runner and heartbeat monitor.

The scenario uses the normal three-group lookahead window (one member per group) so existing operators can seat new membership before the replacement serves. Its Ethereum and Solana signing keys are random, like every operator's, and each receives the standard operator gas/rent funding through an explicit provisioning Step.

Epochs are depot-paced: Ethereum advances only once it has traffic and its minimum has passed. Its epochs here come from the intake itself (an Ethereum → depot message the outpost emits with its reply to the depot's next envelope: the relays report the outpost's backlog to the depot, `sysio.msgch::reportqueue`, which makes Ethereum due), from the redemption's `DESYNDICATE_LIQ` (depot traffic, so the payout drives itself), and from keep-due traffic (`sysio.epoch::notetraffic`) the keep-due pump gives Ethereum while the flow waits for the post-settlement inbound epoch, which nothing queued on either side would bring. The roster consumption and the replacement's deliveries need advances on both chains, so those waits keep both chains (or the chain they read) due the same way.

The pump's `notetraffic` never touches `sysio.epoch::rostersent`, so the roster the outposts consume is one the depot queued by itself: an advance queues the roster only when its hash differs from the one last queued. The flow records each chain's `rostersent` hash before admitting the replacement, fails at once if a row disappears while it waits for both outposts (a `resendroster` would re-ship the roster whatever the diff and mask a roster-propagation regression), and requires both hashes changed once the outposts have consumed the replacement.
